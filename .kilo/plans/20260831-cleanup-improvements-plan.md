# План: улучшения чистки осиротевших ответов и кнопочных команд

Рефакторинг после коммитов 3ff7ec5 и 66b3da8. Принцип чистки (решение пользователя):
«если сообщение, на которое бот ответил, удалено — ответ не нужен; если IP не
мониторится — ответ не нужен».

### 3. Точный фильтр статус-ответов в `cleanupOrphans` (main.go:284)

Идея пользователя: вместо эвристики «любое сообщение бота с IP вне `ips`»
распознавать статус-ответы по строгому формату текста. Текст статуса всегда
`status + " " + ip` (worker.go:109), где `status` — только `"✅"`, `"❗"`
(ping.go:30, worker.go:88) с опциональным суффиксом `"⏸️"` (worker.go:93-94).

Заменить в `cleanupOrphans` условие:

```go
ip := reIP.FindString(tm.Text)
if ip == "" || ips.read(ip) { ... }
```

на проверку префикса статуса + IP (порядок сохранён — сначала префикс):

```go
if !reStatusReply.MatchString(tm.Text) { // ✅⏸️ 1.2.3.4 / ❗ 5.6.7.8 etc
    continue
}
ip := reIP.FindString(tm.Text)
if ip == "" || ips.read(ip) { ... }
```

с регэкспом:

```go
var reStatusReply = regexp.MustCompile(`^(✅|❗)⏸️?\s`)
```

Миграция не нужна: все существующие ответы уже в этом формате. Информационные
сообщения бота с IP больше не могут быть удалены ложно.

### 4. Проверка CLI-запросов при загрузке (закрытие ограничения «MsgID == 0»)

В load-ветке воркера (worker.go:39) сейчас проверяется только `cust.MsgID != 0`.
CLI-подписчики (`MsgID == 0, GlobalID != 0`, global.go:50) не проверяются.
По принципу «нет запроса — нет ответа» добавить симметричную проверку через
`messages.getById` по глобальному id.

Новый хелпер рядом с `msgExists` (vk.go:159):

```go
// report whether a message with the given global id still exists, separating
// a genuine miss (false) from a network/API error (err != nil)
func msgExistsGlobal(peerID, globalID int) (bool, error) {
	res, err := bot.MessagesGetByID(api.Params{
		"peer_id":     peerID,
		"message_ids": globalID,
	})
	if err != nil {
		return false, err
	}
	return len(res.Items) > 0, nil
}
```

Load-ветка (worker.go:39) — заменить

```go
if cust.MsgID != 0 {
    ok, err := msgExists(cust.PeerID, cust.MsgID)
    ...
}
```

на выбор хелпера по типу подписчика:

```go
if cust.MsgID != 0 || cust.GlobalID != 0 {
    var ok bool
    var err error
    if cust.MsgID != 0 {
        ok, err = msgExists(cust.PeerID, cust.MsgID)
    } else {
        ok, err = msgExistsGlobal(cust.PeerID, cust.GlobalID)
    }
    // ... существующая обработка: err != nil — не трогаем; !ok — drop orphan
}
```

Безопасное умолчание сохраняется: при ошибке API (например, групповой токен не
смог получить сообщение) подписчик не удаляется. Учитывать, что CLI-запрос —
исходящее сообщение владельца; если метод на групповом токене для таких
сообщений стабильно возвращает ошибку, проверка фактически деградирует до
«всегда сохранять» — это безопасно, но задокументировать поведение в логе
(`let.Println("msgExistsGlobal", cust, err)` уже покрывает).

## Риски

- `reStatusReply` зависит от формата статусов; при добавлении новых статусов
  (не ✅/❗) регэксп нужно расширить — место рядом с ним задокументировать.
- `messages.getById` на групповом токене может не отдавать исходящие сообщения
  владельца — проверка CLI деградирует до безопасного «сохранять» (не ломает).

## Постфикс: баги, найденные при проверке (2026-08-31)

1. **Регэксп `^(✅|❗)⏸️?\s` был неверен**: `?` связывался только с variation
   selector `️` (U+FE0F) после `⏸`, делая сам `⏸` обязательным. Статусы без
   `⏸️` (например `✅ 127.0.0.1`) не распознавались. Фикс:
   `^(✅|❗)(?:⏸️)?\s` (global.go).
2. **Удаление статуса по cmid не работало**: `ReplyID` в `customer` — на самом
   деле **глобальный** id ответа (его возвращает `messages.send`), а не
   conversation id (в диалоге владельца cmid ≠ глобальный id: например,
   глобальный 822 ↔ cmid 572 — видно в ответе `messages.delete`).
   Диагностика показала: `messages.delete(peer_id, message_ids=ReplyID)`
   удаляет корректно, а резолв `ReplyID` как cmid через
   `getByConversationMessageID` возвращает пусто («deleteReply gone») и
   удаление молча скипается. `deleteReply` упрощён до прямого вызова
   `deleteMessage`; в `deleteMessage` добавлены лог ответа и проверка
   пер-идентификаторных ошибок (VK отдаёт их с HTTP 200); комментарий поля
   `ReplyID` в global.go исправлен.
3. **`msgExistsGlobal` падал** («One of (peer_id, cmids) is undefined»): при
   переданном `peer_id` API ждёт `cmids`, а не `message_ids`. `peer_id` убран —
   `messages.getById` работает по глобальным id без него.
4. Замечен гоночный нюанс: воркер, чей единственный подписчик сброшен как
   сирота, остаётся жив (`ips.read` = true), поэтому `cleanupOrphans` такой IP
   пропускает — но ответ теперь удаляет сам воркер (п.2), так что в итоге
   сирота убирается. Гонка «cleanupOrphans читает историю раньше, чем воркер
   удалил» безвредна: оба удаления идемпотентны.
5. **Рестарт не чистил ответы мониторящихся IP с удалённым запросом**:
   `cleanupOrphans` по дизайну пропускает мониторящиеся IP, а воркер проверял
   запросы только при загрузке. Добавлен сигнал `cmdVerify = "❓"`
   (main.go): `restart()` рассылает его воркерам, каждый перепроверяет запросы
   подписчиков (`requestExists`), дропает сирот с удалением
   ответа через `unsub`; при пустом `cus` воркер завершается и
   `defer ips.del` снимает IP с мониторинга, после чего `cleanupOrphans`
   (вызываемый следом, последовательно) подчищает остальное.

## Семантика отписки (решение 2026-08-31, вопрос адресности ❌)

Механизм кнопки ❌: payload `"…[статус]❌"` → `ips.update` — **групповая**
рассылка всем воркерам, отбор по совпадению `tsX` со `status` воркера;
воркер отписывает всех своих подписчиков и завершается. Адресации по
пользователю или IP в кнопке **нет** (работает «адресно» только потому, что у
IP обычно один подписчик).

События `message_delete` в community LongPoll нет, поэтому «нажать ❌» в
момент удаления запроса невозможно. Эквивалент реализован опросом:
`cmdVerify` при старте/рестарте проверяет `requestExists` по каждому
подписчику и для отсутствующих выполняет тот же путь `unsub` — с более
точной адресацией (по конкретному подписчику, а не по статусу воркера).

Решение пользователя: кнопку ❌ адресной (payload с IP + фильтр `cus` по
`UserID`) **не делать** — остаётся групповой по статусу. Изменение кода не
требуется, текущая реализация соответствует этому решению.

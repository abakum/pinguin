# Замена подписки при повторном триггере на тот же хост

## Проблема

Повторный триггер (сообщение с IP) от того же пользователя в том же чате создаёт
**дубликат** подписки вместо замены:

- `bhAnyWithMatch` (main.go:474) на каждый триггер вызывает `ips.write(ip, customer{PeerID, UserID, MsgID})`.
- Ветка `//subscribe` воркера (worker.go:128) делает `cus = append(cus, cust)` без проверки на существующую запись с теми же `PeerID`+`UserID`.
- В цикле ответов (worker.go:163) у новой записи `ReplyID == 0` → отправляется **второй** статусный ответ на новое сообщение-запрос; старый ответ остаётся.
- Дубликаты попадают в `pinguin.json` (сохранение всех `cus`), а после каждого рестарта `catchUp` (main.go:395) реплеит триггеры и **добавляет ещё по дубликату** на каждый запрос.

Итог: несколько ответов и записей на один хост на одного пользователя в одном чате.

## Решение

Дедупликация по ключу `(PeerID, UserID)` **внутри воркера** — единая логика для
всех источников подписок (обычный триггер, CLI-триггер через `message_reply`,
загрузка из `pinguin.json`). При совпадении ключа: старая запись удаляется, её
статусный ответ удаляется (`unsub` → `deleteReply`), новая запись занимает её
место. Для нового триггера `ReplyID == 0`, поэтому существующий цикл ответов
сам создаст свежий ответ, привязанный к новому сообщению-запросу.

Дедупликация выполняется в **обеих** ветках воркера (решение подтверждено пользователем):

1. `//subscribe` (worker.go:128) — новые триггеры;
2. `//load` (`cust.Cmd == ip`, worker.go:44) — загрузка из `pinguin.json`,
   чтобы убрать уже накопившиеся дубликаты (оставляется самая поздняя запись,
   ответы более ранних дубликатов удаляются).

Править нужно только `worker.go`; `main.go`, `vk.go`, `json.go` не меняются.

## Изменения (worker.go)

Рядом с замыканием `unsub` (worker.go:23) добавить замыкание по тому же образцу
(идиома фильтра `kept := cus[:0]` уже используется в ветках `cmdVerify` и `❎`):

```go
// upsert a subscription: an entry with the same peer+user is replaced -
// its old status reply is deleted (see unsub), the new request takes its
// place; catches re-triggers and duplicate loads of the same host
upsert := func(cust customer) {
	kept := cus[:0]
	for _, cu := range cus {
		if cu.PeerID == cust.PeerID && cu.UserID == cust.UserID {
			ltf.Println("resubscribe", cu)
			unsub(cu)
			continue
		}
		kept = append(kept, cu)
	}
	cus = append(kept, cust)
}
```

Затем заменить оба `cus = append(cus, cust)`:

- ветка load (worker.go:55): после уже существующей проверки `requestExists`
  (порядок сохранить: orphan-drop сначала, потом upsert);
- ветка subscribe (worker.go:129).

## Поведение после изменения

- Повторный триггер тем же пользователем в том же чате: старый ответ удалён,
  создан новый, привязанный к новому сообщению-запросу; в `cus` и в
  `pinguin.json` — одна запись на `(ip, PeerID, UserID)`.
- Загрузка с дубликатами в `pinguin.json`: остаётся самая поздняя запись (её
  `ReplyID` валиден, ответ не пересоздаётся лишний раз), ответы остальных
  дубликатов удаляются.
- `catchUp` после рестарта больше не плодит дубликаты: реплей триггера
  заменяет загруженную подписку (старый ответ удаляется, создаётся новый).

## Граничные случаи (без изменений поведения)

- Тот же пользователь, тот же хост, **другой чат**: `PeerID` другой → обе
  подписки сосуществуют, как раньше (требование «в этом чате»).
- Другой пользователь, тот же чат, тот же хост: `UserID` другой → у каждого
  свой ответ.
- Несколько IP в одном сообщении: обрабатываются независимо (`set()` в
  `bhAnyWithMatch` уже убирает повторы IP).
- Ошибка `deleteReply` (ответ уже удалён вручную): логируется, не фатально
  (существующее поведение `unsub`).
- Внешняя ⏸️ (`cust.ReplyID != 0`): работает по `UserID` после upsert без
  изменений.

## Риски

- Дополнительные вызовы VK API (delete + send) при повторном триггере — те же
  два вызова, что и при смене статуса; лимиты не напрягаются.

## Проверка

1. `go vet ./...`, `go mod tidy`, `go build ./...` (полная сборка — `make win`).
2. Ручные сценарии:
   - «Локал 1.2.3.4» → ответ есть; повторить тот же IP тем же пользователем →
     старый ответ исчез, новый привязан к новому сообщению, в панели `…` автор
     один;
   - тот же IP от другого пользователя в том же чате → два независимых ответа;
   - тот же IP тем же пользователем в другом чате → обе подписки живут;
   - рестарт при наличии дубликатов в `pinguin.json` → после загрузки остаётся
     один ответ на подписку, реплей триггера из `catchUp` не добавляет новый.
